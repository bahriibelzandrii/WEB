## Lab 3 — форми та серверна валідація (2026-09-21)

| # | Рішення | Обрано | Обґрунтування |
|---|---|---|---|
| D30 | Межі Lab 3 | CRUD довідників: клієнти, пристрої, роботи + каталог запчастин `/parts`; форми **без** `required` — валідація тільки на сервері | Тема ЛР — форми та серверна валідація; `required` приховує серверну логіку від користувача (браузер не дає відправити порожню форму) |
| D31 | Валідація форм | Єдине джерело правди — контролер: збір **усіх** помилок → `400` + повторний рендер форми з `errors` + старими значеннями (PRG); спільні хелпери в `src/lib/validate.ts` (`clean`, `toNumber`, `tooLong`, `isEmail`, `isPhone`, `parseDateOnly`, `isUniqueViolation`) | Дублювання правил у клієнті/сервері — класична пастка; спільні хелпери уникли розбіжностей між 4 модулями; `400` + список помилок — канонічний SSR-патерн (D28) |
| D32 | Каталог запчастин | Повний CRUD `/parts` (список/створення/редагування), `sku` — optional + унікальний, `price` — число ≥ 0 | `Part` існувала в моделі (D2) без веб-шару; каталог — четвертий довідник, показує повторюваність патерну |
| D33 | Redirect після створення | Клієнт/пристрій → картка `/clients/:id`, `/devices/:id`; роботи/запчастини → список (карток немає) | Картка — найкоротший шлях подальших дій (редагування, перегляд історії); для рядків каталогу картка відсутня за проєктом (D20) |
| D34 | Date-only поля | `purchasedAt` зберігається як **UTC-опівночі** (`parseDateOnly` в `lib/validate.ts`), форма редагування рендерить `toISOString().slice(0, 10)` | Локальне опівночі + UTC-рендер давало зсув на день назад у UTC+ (перевірено E2E); seed і так писав `new Date("YYYY-MM-DD")` = UTC — тепер формі і seed однаково |
| D35 | Видалення даних | `POST /:id/delete` у 4 модулях; клієнти/пристрої — **soft delete** (`deletedAt`, 404 для видаленого), роботи — hard delete + `RequestWork.catalogId → null` (snapshot у заявках зберігається), запчастини — hard delete з охороною: якщо `RequestPart` посилається → `400` + список із повідомленням; UI: кнопка «Видалити» (.btn-danger) у списках (колонка «Дії») і на картках/формах редагування — посилання на серверну сторінку підтвердження (D39), далі POST без даних | Клієнти/пристрої — учасники історії заявок (NULL-заборона у моделі, D2), тому рядок лишається в БД; записи каталогів у заявках — snapshot значень, тому їх безпечно знищувати остаточно |
| D36 | «Розумні» валідатори | Поглиблена серверна валідація полів: українські номери телефонів `isUaPhone` (`+380` + 9 цифр або `0` + 9 цифр), ціни та тривалість > 0 із `maxDecimals ≤ 2` (до 2 знаків після коми), дати покупки не в майбутньому та не раніше 1990 року (`MIN_DATE = 1990-01-01`), імена/бренди/моделі/назви — мінімум 2 символи, SKU — 2–50 символів (`^[A-Za-z0-9][A-Za-z0-9-]*$`), опис заявки — 5–500 символів, email — до 320 символів | Захист цілісності бізнес-даних від сміттєвих значень (1 символ, нульові ціни, некоректні телефони), єдиний стандарт повідомлень про помилки у всіх формах (137 перевірок E2E) |
| D37 | Розміщення кнопок у шапці карток (`.page-head`) | Навігаційна кнопка `← Назад` — у правому верхньому куті (`.page-head-top`), кнопки дій сутності (`Редагувати`, `Видалити` або переходи статусів) — знизу ліворуч під метаданими (`.page-actions`). У списках кнопка створення — праворуч від заголовка | Чітке функціональне розділення навігації назад і дій над об'єктом за макетом замовника; запобігання скупченню кнопок різного призначення |
| D38 | Розмітка кнопок дій у формах (`.form-actions`) | `display: flex; gap: 12px; align-items: center; margin-top: 24px;` у `style.css`. Кнопку «Видалити» перенесено на лівий край панелі дій перед «Зберегти» та «Скасувати», уніфіковано розмір кнопки | Ліквідація злипання кнопок у купу на формах редагування та створення; розташування кнопки видалення на лівому краї з комфортним простором між діями |
| D39 | Підтвердження видалення без браузерного `confirm()` | Кнопка «Видалити» (.btn-danger) — посилання на `GET /:id/delete` (спільний `views/confirm-delete.pug`: підсумок запису, «Так, видалити» → `POST /:id/delete` без даних, «Скасувати»); POST, 404 та 400-захист використаних запчастин — без змін | Браузерний `confirm()` не піддається автотестуванню, не працює без JS і блокується розширеннями; серверна сторінка — автотестована (lab3-e2e) і відповідає стилю застосунку; суперседує UI-чассину D35 |
| D40 | Заявки: видалення, повне редагування, рядки робіт/запчастин, фільтр пристроїв за клієнтом | 1) `GET/POST /requests/:id/delete` — серверне підтвердження + soft delete (`deletedAt`, далі 404, список не містить). 2) Форма редагування — **всі** поля: тип (з fallback на поточний), пріоритет, опис, клієнт, пристрій, майстер, гарантійне посилання (лише для WARRANTY_CLAIM, список `NOT: { id }`). 3) Картка заявки — додавання/видалення рядків: `POST /:id/works(+/ :lineId/delete)`, `POST /:id/parts(+/ :lineId/delete)`, інлайн-форми з каталогів, JS-префіл ціни/годин з `data-*` опцій, суми «Разом» у реальному часу. 4) Фільтр: option'и select пристроїв несуть `data-owner`; JS ховає чужі пристрої при виборі клієнта; **сервер** у create та edit перевіряє `device.ownerId === clientId` (400 «Пристрій не належить обраному клієнту»); «новий клієнт» → «новий пристрій» (лок у JS + 400 на сервері). Майстер — select тільки `role = TECHNICIAN` | Soft delete узгоджений із D16 (soft delete для сутностей, що несуть історію) і UI D39; повне редагування видаляє обмеження D24, бо тепер тип/власність/гарантія коректно валідуються на сервері (D31); рядки — мінімальний CRUD на `RequestWork`/`RequestPart` без оцінки (она формується окремо, D13); фільтр-це-UX-підказка, а інваріант власності (D8) дотримує сервер — клієнтський JS не є захистом |
| D41 | Seed: узгодженість «клієнт ↔ пристрій» | Seed гарантує `device.ownerId === request.clientId` для **кожної** заявки: ручні 15 заявок — явний вибір пристроїв свого клієнта (власники 0–7 мають ≥1 пристрій у `DEVICES`); 33 згенеровані пристрої — `ownerIdx = i % clients.length` (round-robin → кожен із 30 клієнтів має ≥1); `generateRequests` обирає пристрій **лише з пулу власника** вибраного клієнта | Після D40 сервер відхиляє некоректну пару, тому старий seed (55/60 заявок із «чужим» пристроєм) робив неможливим збереження більшості історичних заявок через форму — seed був головним споживачем нових правил; round-robin + фільтр пулу — детерміновано (`mulberry32`), кількість записів не змінюється (60/30/45) |
| D42 | Секції картки заявки: інтерактивні форми + файл-завантаження | 9 POST-роутів на картці: діагностика (upsert 1—1), оцінка (створити/оновити/затвердити/відхилити), рахунок (видати з затвердженої оцінки + платежі з контролем залишку), гарантія (upsert, термін з фіксованого набору), коментарі (з прапорцем внутрішній), вкладення (multipart через `busboy`). Файли — каталог `uploads/` (named volume у Docker, `mkdir+chown` в образі **до** `USER node`), статика `GET /uploads/*`, ім'я санітується + суфікс при конфлікті. | D43 | UX картки: збереження позиції прокрутки + фікс секції «Гарантійне посилання» | 1) Bug: у `show.pug` блок тексту був **по-за** викликом mixin `+section(…)` (рівень відступу pug) → `<p>` рендерився поза карткою; виправлено вкладенням під виклик. 2) Scroll: скрипт у `layout.pug` — при submit будь-якої форми зберігає у `sessionStorage` URL, `form.action`, відстань форми від верху viewport; після повного перевантаження (PRG) сторінка скролиться до тієї ж форми з тим самим офсетом (fallback — записаний `scrollY`; маркер одноразовий, TTL 60 с) | Завдання користувача: дані мають оновлюватись «на місці» без перекидання вгору. Обрано мінімальний шлях (sessionStorage + scrollTo), а не fetch/SPA-заміну DOM: працює з усіма 9 формами + інлайн-формами, у т.ч. multipart-завантаженням, без зміни серверу; PRG/валідація 400 зберігаються без змін |
