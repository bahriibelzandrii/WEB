## Platform

web

## Users

Персонал невеликого сервісного центру (СЦ) з ремонту комп'ютерної техніки:

- **Технік** — приймає пристрій у ремонт, веде картку заявки: діагностика, оцінка, вкладки/коментарі.
- **Клієнт** (Lab 4) — власник пристрою зі своїм акаунтом: бачить лише статус своїх замовлень
  (список «Мої замовлення» + скорочена картка з фінансами).
- **Бухгалтерія** — рахунки, платежі, гарантії.

Від Lab 4: роль **менеджера зникла** (її функції розподілені між техніком та
адміністратором), а клієнти — повноправні користувачі: прив'язка
`Client.userId` дає кожному акаунту ролі КЛІЄНТ власні замовлення.
Відвідувач (реєстрація без персоналу) — read-only перегляд; гостю без входу
доступний лише лендінг.

## Product Purpose

Університетська веб-лабораторна (Lab_3: «Форми та серверна валідація») — робочий
демо-сайт СЦ, який замість статичної сторінки показує повний робочий цикл ремонту:
заявка → діагностика → оцінка → рахунок/платежі → гарантія.

**Успіх:** серверно-рендерений сайт, де кожен ввід користувача валідується на сервері
(HTTP 400 + банер помилок + збережені значення форм), весь функціонал покритий
автоматизованим тестуванням (e2e 186 + web-check 48 + інваріанти 10) і задокументований
(`docs/PAGES.md`, `docs/TEST_PLAN.md`, `docs/DECISIONS.md`). Завантажувач — викладач;
контекст оцінки — захист/перевірка лабораторної.

## Positioning

Демонстрація **server-driven UX** як архітектурної позиції: браузер — тупий клієнт,
весь стан і правила — на сервері. Форми → PRG → валідація → 400/redirect. Картка
заявки (`GET /requests/:id`) агрегує 9 POST-роутів секцій (діагностика, оцінка,
approve/reject, рахунок, платежі, гарантія, коментарі, вкладення) з жорсткими
серверними інваріантами (статуси, суми, 1-на-1 upsert). Це те, що не зможе скопіювати
«та сама сторінка, але з client-side валідацією»: тут немає жодної клієнтської
проверки — кожен чек виконується в контролерах.

## Operating Context

Локальний розробочий цикл (Windows + Git-Bash + Docker):

- `docker compose up` — `lab2_service_app` (Node 24, tsx) + `lab1_service_db` (PostgreSQL 18).
- `npm run seed` — демо-дані; e2e-сценарій чистить свої залишки сам.
- Перевірки: `bash scripts/lab3-e2e.sh` (186, **вимагає свіжий том** `docker compose down -v`),
  `npm run check:web` (48, Playwright), `npm run check` (10 інваріантів БД).
- UI-мова — українська; всі назви, статуси, валідаційні повідомлення UA.
- Завантаження файлів (вкладення) — `busboy`, каталог `uploads/` (named volume у Docker).

## Capabilities and Constraints

- **Стек (застереження, не рішень):** TypeScript (tsx), Express 5, Prisma 7 + PostgreSQL 18,
  Pug 3 (server rendering), busboy. **Без SPA/JS-фреймворків** — клієнтський JS лише
  мінімальні inline-скрипти (напр. scroll-restore, D43).
- **Ролей і авторизації немає** — одна демо-сесія на всіх; це обмеження завдання, не проєкту.
- **Правила домену (серверні інваріанти, `scripts/check-invariants.ts`):** фіксовані
  enums статусів заявок/рахунків; суми ≥ 0 з до 2 знаками; upsert 1-на-1
  (діагностика/оцінка/рахунок/гарантія на заявку); endDate гарантії = start + термін;
  рахунок — лише з затвердженої оцінки; платежі не перевищують залишок.
- **Контракти форм:** кожна форма — POST + валідація + 400 з банером; значення
  форм зберігаються при помилках (PRG).
- **Мовний контент:** лише українська; i18n не передбачено.
- Відкритих продуктових рішень немає; технічні — див. `docs/DECISIONS.md` (D1–D43).

## Product Principles

1. **Сервер — єдиний джерело правди.** Жодної клієнтської валідації і стану;
   JS у браузері — лише зручності, які не ламають UX без себе.
2. **Кожен ввід — контракт.** Погане значення повертається 400 + конкретним
   UA-повідомленням + збереженими полями; ніколи мовчазного «нічого не сталося».
3. **Автоматика замість ручних кліків.** Будь-яка поведінка має тест; новий фіч —
   нові перевірки в e2e/web-check (звіт 186/48/10 є частиною «готово»).
4. **Документи живуть разом з кодом.** Кожне рішення — рядок у `DECISIONS.md`,
   кожна зміна розкладки — оновлення `PAGES.md` в тому ж замітанні.
