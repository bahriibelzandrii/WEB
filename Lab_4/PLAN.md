# PLAN (Lab 2) — Контролери та представлення

Step-by-step план реалізації веб-шару (контролери + Pug-шаблони) на базі Lab 1.
Кожен крок має **команди** та **критерій приймання** — крок завершено, лише коли
критерій виконано.

**Джерела правди:** `docs/PAGES.md` (спека сторінок), `docs/DATA_MODEL.md` (модель,
статусна машина, інваріанти), `docs/DECISIONS.md` (D19–D28 — рішення Lab 2).

**Не змінюємо ядро Lab 1:** `prisma/schema.prisma`, міграції, `seed.ts`,
`check-invariants.ts`, `docker-compose.yml`, `.env`, `start.bat`/`stop.bat`.

## Фаза 0. Каркас представлень

### Крок 0.1 — Залежність pug
`npm i -E pug@3.0.4` (точний pin).

**Приймання:** `npm ls pug` → рівно `3.0.4`; `package.json` оновлено.

### Крок 0.2 — `src/index.ts`: view engine + static + парсери
`app.set('view engine', 'pug')`, `express.static('public')`,
`express.urlencoded({ extended: false })`; `/health` лишається.

### Крок 0.3 — Layout і partials
`views/layout.pug` (head: title, `/css/style.css`; header/footer через partials),
`views/partials/{header,footer,flash}.pug`, `public/css/style.css` (база: layout,
навігація, таблиці, бейджі, форми, пагінація — за `PAGES.md` §5).

**Приймання:** тимчасовий `GET /` рендерить layout (заголовок + навігація + CSS);
`/nonexistent` → ще 404 Express (у кроці 0.4 замінимо).

### Крок 0.4 — 404 / 500
`views/errors/{404,500}.pug`; `app.use(notFound)` + error-handler в `index.ts`.

**Приймання:** `GET /nonexistent` → стилізована 404; штучний `throw` → 500 сторінка.

## Фаза 5. Створення заявки

### Крок 5.1 — `requests.createForm` + `views/requests/create.pug`
Форма за §4.4: тип/пріоритет/опис, клієнт (існуючий/новий), пристрій
(існуючий/новий), майстер, warranty-select; vanilla JS для показу блоків.

### Крок 5.2 — `requests.create`
Валідація (усі помилки збираються) → 400 + повторний рендер з `errors`/`values`;
успіх → `$transaction` (клієнт? → пристрій? → номер `R-YYYY-NNNN` → заявка,
`createdById` = ADMIN) → PRG на картку.

**Приймання:**
- порожня форма → 400 зі списком помилок, значення збережені;
- створити з існуючими клієнтом/пристроєм → номер `R-2026-NNNN` (max+1),
  статус NEW, redirect на картку;
- створити з новим клієнтом + новим пристроєм (ownerId = новий клієнт);
- WARRANTY_CLAIM: без вибору оригіналу → помилка; з COMPLETED-заявкою →
  `originalRequestId` записаний, на картці — посилання;
- `npm run check` → інваріанти цілі.

## Фаза 6. Редагування + переходи статусів

### Крок 6.1 — `requests.editForm` / `requests.edit`
Форма: опис, пріоритет, майстер, клієнт, пристрій (§4.5). Валідація → 400/PRG.

### Крок 6.2 — `requests.transition`
`POST /requests/:id/transition`: `canTransition` (§4.6); заборонений →
`?error=transition` (банер на картці).

**Приймання:**
- зміна опису/пріоритету зберігається; номер/тип/статус не змінюються;
- валідний перехід (NEW → IN_DIAGNOSTICS) → статус змінено;
- заборонений (NEW → COMPLETED) → банер, статус не змінився;
- з COMPLETED/CANCELED кнопок переходів немає.

## Ризики та плани «Б»

| Ризик | Ймовірність | План «Б» |
|---|---|---|
| Pug-синтаксис (вкладеність, mixings) — типові помилки перших сторінок | висока | писати по одній сторінці, запускати сервер після кожної; pug дає чіткі помилки compile-time |
| `groupBy` + enum у Prisma 7 — дрібні нюанси типів | низька | fallback: 7 окремих `count` замість `groupBy` |
| Decimal у Pug (Drift/Decimal-об'єкт) | середня | завжди через `format.uah()` до рендеру |
| Порт 3000 зайнятий | низька | `PORT=3001 npm start` (`.env` підтримує) |
| Час на «максимум» (грошова частина) | — | усвідомлено відкинуто (D20): read-only в картці заявки |
