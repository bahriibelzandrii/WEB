# Lab 4. Авторизація та ролі: «Сервіс ремонту та обслуговування комп'ютерної техніки»

Університетська лабораторна робота: **реалізація авторизації користувачів**
(Passport.js, сесії) та **налаштування захищених точок доступу**
(контролери/дії за ролями) на базі Lab 3.

Ланцюг розробки (кожна лаба — продовження попередньої, оригінальні папки
не змінюються):

- **Lab 1** — реляційна модель даних (15 сутностей, 9 enum, seed, інваріанти І1–І10).
- **Lab 2** — веб-шар: Pug-шаблони, MVC, 13 сторінок.
- **Lab 3** — форми та серверна валідація: CRUD довідників, каталог запчастин.
- **Lab 4** — **авторизація**: 4 ролі (адміністратор, майстер, клієнт,
  відвідувач), вхід/вихід/реєстрація, захист маршрутів, сторінка 403,
  лендінг для гостя, особистий кабінет, клієнтська зона «Мої замовлення».

## Ролі та матриця дозволів

Міграціями Lab 4 роль `MANAGER` замінено на **`CLIENT` (клієнт)**
(`ALTER TYPE "Role" RENAME VALUE 'MANAGER' TO 'CLIENT'`), а четверту роль
— **`VISITOR` (відвідувач)** — додано (`ALTER TYPE "Role" ADD VALUE`).

Правила захисту (`src/lib/auth.ts`):

1. **Гість** без входу бачить лише лендінг `/`; будь-який інший маршрут —
   `302` редірект на `/login?next=<повернення>` (глобальний `guestGate`).
2. **Авторизований без потрібної ролі** → `403` (`views/errors/403.pug`)
   з поясненням, яка роль потрібна.
3. Домівка після входу (`homeFor`): клієнт → `/requests/my-orders`,
   решта → `/dashboard`; авторизований, який відкриває `/`, отримує
   редірект на свою домівку.

## Нові сторінки та поведінка

| Маршрут | Опис |
|---|---|
| `GET /` | гостю — маркетинговий лендінг (без БД); авторизованому — редірект на свою домівку |
| `GET /login` | форма входу (email + пароль); запит `?next=` — куди повернутись після входу |
| `POST /login` | Passport.js `local` strategy → `bcrypt.compare`; успіх → редірект (або `next`), помилка → 401 + повторна форма з помилкою |
| `GET /logout` | знищення сесії → `/login?loggedout=1` |
| `GET /register` | публічна реєстрація (нові акаунти — роль `VISITOR`) |
| `POST /register` | серверна валідація (Lab 3 паттерн: 400 + `errors[]` + збережені значення); унікальність email; успіх → автовхід → домівка |
| `GET /requests/my-orders` | (КЛІЄНТ) список власних замовлень через `Client.userId` |
| `GET /requests/:id` | (КЛІЄНТ) скорочена картка тільки своїх заявок: статус, опис, пристрій, діагностика, оцінка/рахунок/оплати, гарантія |
| `GET /cabinet` | (авторизовані) особистий кабінет: профіль + зміна пароля |
| `POST /cabinet/profile` | оновлення імені/email/телефону (валідація: ім'я ≥2, унікальний email, телефон UA-формат або порожній) |
| `POST /cabinet/password` | зміна пароля (поточний ≥6, новий ≥8, підтвердження збігається) |
| `403` | сторінка «Доступ заборонено» з назвою потрібної ролі |
| `GET /health` | без змін (JSON) |

Кожна мутуюча дія Lab 3 отримала вейдер за матрицею (таблиця вище):
`routes/requests.ts`, `routes/clients.ts`, `routes/devices.ts`,
`routes/works.ts`, `routes/parts.ts`.

## Зміни моделі (міграції)

`prisma/migrations/20261018000000_add_visitor_role/`:

```sql
ALTER TYPE "Role" ADD VALUE 'VISITOR';
```

`prisma/migrations/20261018120000_replace_manager_with_client/`:

```sql
ALTER TYPE "Role" RENAME VALUE 'MANAGER' TO 'CLIENT';
ALTER TABLE "User" ALTER COLUMN "role" SET DEFAULT 'CLIENT';
ALTER TABLE "Client" ADD COLUMN "userId" TEXT; -- FK → User(id), UNIQUE, ON DELETE SET NULL
```

`prisma/seed.ts`: акаунти `admin@`, `client@`, `tech1@`, `tech2@`,
`visitor@service.ua` (пароль `Secret123`); `client@` прив'язаний до
клієнта, якому належить замовлення `R-2026-0001` (NEW, призначене tech1).

## Сесії

- `express-session`, секрет — `SESSION_SECRET` (`.env.example`), cookie
  `httpOnly` + `sameSite=lax`, `maxAge` 8 годин, `saveUninitialized: false`.
- У сесії зберігається **лише id користувача** (serializeUser/deserializeUser);
  роль читається з БД на кожному запиті — зміна ролі діє негайно.

## One-click launch (Windows)

Подвійний клік **`start.bat`** — перевіряє Docker, збирає образ, піднімає
PostgreSQL 18 + додаток, застосовує міграції (включно з новими Lab 4),
насичує демо-даними, запускає сервер → **http://localhost:3000**.

Зупинити все — **`stop.bat`** (скинути дані: `docker compose down -v`).

## Тест-план (ручна/автоматична перевірка)

1. Гість: `GET /` — 200 (лендінг, кнопка «Увійти»); `GET /dashboard` →
   `302 /login?next=/dashboard`; після входу повернення на `/dashboard`.
2. `POST /login` з помилковим паролем — 401, банер «Невірний email або пароль».
3. Вхід `visitor@service.ua` / `Secret123` — редірект на дашборд;
   `GET /requests/new` → **403**, `GET /clients/new` → **403**.
4. Вхід `client@service.ua` — редірект на `/requests/my-orders`;
   список містить `R-2026-0001`; чужа картка та `/dashboard`, `/requests`,
   `/clients` → **403**.
5. Вхід `tech1@service.ua`:
   - `GET /requests` — тільки призначені йому заявки (у seed — `R-2026-0001`);
   - `GET /requests/new`, `/clients/new`, `/works/new` → **200**;
   - на картці заявки — форми робіт/запчастин/діагностики/оцінки.
6. Вхід `admin@service.ua` — бачить усі заявки, доступ до всього,
   включно з видаленням.
7. Кабінет: `GET /cabinet` — 200 (адмін/майстер/клієнт/відвідувач);
   `POST /cabinet/profile` з порожнім іменем — 400;
   `POST /cabinet/password` зі старим/новим/підтвердженням — 302.
8. `GET /logout` → на `/login` з банером «Ви вийшли з системи».
9. `POST /register` (новий email + пароль ≥8) — акаунт створюється,
   авто-логін, роль «Відвідувач»; повторний реєстр на той самий email —
   400 «Email уже використовується».
10. Автоматичний smoke-сценарій (69 перевірок): `scripts/lab4-smoke.ps1`
    — гостеві сценарії, всі ролі, кабінет, реєстрація:
    `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/lab4-smoke.ps1`.
