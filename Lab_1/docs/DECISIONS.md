# Журнал проєктних рішень

Кожен пункт — рішення, узгоджене в ході проєктування (grill-інтерв'ю, 2026-09-14).

| # | Рішення | Обрано | Обґрунтування |
|---|---|---|---|
| D1 | Межі системи | базове ядро: клієнти, обладнання, заявки, діагностика, роботи, оплати | Фокус ЛР — модель даних, а не портал/CRM. Склад, договори, бронювання, відгуки, доставка — відкинуто |
| D2 | Запчастини | каталог `Part` + позиції `RequestPart` **без складу** | Запчастини — грошова стаття оцінки; облік залишків виходить за межі теми |
| D3 | Framework | **Express.js 5.2.1** | Найпоширеніший, мінімум «магії», модель даних лишається в центрі |
| D4 | ORM | **Prisma 7.10.0** | Schema-first: вся модель в одному `schema.prisma` — ідеально для ЛР на модель даних; міграції з коробки |
| D5 | База даних | **PostgreSQL 18 у Docker** | Потрібна портативність на інший ПК (docker-compose = одна команда) + повноцінна БД з нативними enum (SQLite enum не має) |
| D6 | Версії | найновіший **стабільний** стек, жорсткі pin | Node 24 LTS, Express 5.2.1, Prisma 7.10.0, TS 7.0.2, PG 18. Prisma 8 (RC) та Express 6 (не випущено) — не стабільні. Pin захищає від npm-тегу `latest` → RC |
| D7 | Актори | `Client` — окрема сутність (без акаунтів), `User` з роллю (ADMIN/MANAGER/TECHNICIAN) | Онлайн-бронювання відкинуто → клієнтам акаунти не потрібні |
| D8 | Обладнання | окрема сутність `Device` з історією (1—N заявок), власник — Client | Історія ремонту конкретного приладу — цінний бізнес-зріз; одна заявка = один прилад |
| D9 | Життєвий цикл заявки | 7 статусів: NEW → IN_DIAGNOSTICS → ESTIMATE_READY → IN_REPAIR → READY → COMPLETED + CANCELED | Повний реальний цикл майстерні, включно з очікуванням рішення клієнта по оцінці |
| D10 | Тип заявки | REPAIR / MAINTENANCE / WARRANTY_CLAIM + пріоритет LOW/NORMAL/HIGH/URGENT | «Обслуговування» з теми — окремий тип (превентивна обслуговка), а не договір |
| D11 | Роботи | `WorkCatalog` (прайс) + `RequestWork` (позиція зі снапшотом ціни, майстром, статусом) | Прайс-лист + гнучкість; снапшот ціни зберігає історію при змінах прайсу |
| D12 | Діагностика | окрема сутність `Diagnostics` (1—1 із заявкою) | Діагностика має висновок, майстра і власну вартість |
| D13 | Гроші | 3 сутності: `Estimate` → `Invoice` → `Payment` | Повна грошова історія: оцінка (draft/approved/rejected), рахунок зі знижкою, часткові оплати |
| D14 | Гарантія | сутність `Warranty` (1—1 із завершеною заявкою) + self-reference `originalRequestId` у Request | Гарантійне звернення пов'язане з оригінальним ремонтом |
| D15 | Комунікація | `Comment` (з прапорцем isInternal) + `FileAttachment` | Жива модель заявки без ускладнення |
| D16 | Технічні деталі | createdAt/updatedAt скрізь; soft delete на Client/Device/Request; Decimal(10,2); нативні enum | Стандартний набір; soft delete — там, де видалення руйнує історію |
| D17 | Артефакти | повний пакет: schema + міграції + seed + ER + документація + docker-compose | Без CRUD API (не входить у завдання), але проєкт запускається як додаток |
| D18 | Валюта | UAH, без поля currency | Одна країна обслуговування; поле валюти — зайва складність |
