# Lab 5. Захищена адмін-область: «Сервіс ремонту та обслуговування комп'ютерної техніки»

Університетська лабораторна робота: **захищена область, де авторизований
користувач із необхідними повноваженнями управляє даними системи**
(додавання / редагування / видалення записів **всіх 15 таблиць**) на базі Lab 4.

Ланцюг розробки (кожна лаба — продовження попередньої, оригінальні папки
не змінюються):

- **Lab 1** — реляційна модель даних (15 сутностей, 9 enum, seed, інваріанти І1–І10).
- **Lab 2** — веб-шар: Pug-шаблони, MVC, 13 сторінок.
- **Lab 3** — форми та серверна валідація: CRUD довідників, каталог запчастин.
- **Lab 4** — авторизація: 4 ролі, вхід/вихід/реєстрація, `requireRole`, 403.
- **Lab 5** — **захищена область керування**: модуль користувачів (адмін),
  role-aware інтерфейс (кнопки/форми видимі за ролью), повне CRUD-покрытие
  всіх 15 таблиць за матрицею дозволів.

## Модуль «Користувачі» (нове, Lab 5)

Тільки **адміністратор** (вейдер `requireRole(["ADMIN"])` + `can.admin` в UI):

| Маршрут | Опис |
|---|---|
| `GET /users` | список користувачів + пошук (ім'я/email/телефон) |
| `GET /users/new` / `POST /users` | створення: ім'я, email (унікальний), телефон, роль, пароль ≥6 (bcrypt) |
| `GET /users/:id/edit` / `POST /users/:id/edit` | зміна даних/ролі; пароль — лише якщо вказано новий |
| `GET /users/:id/delete` / `POST /users/:id/delete` | підтвердження (server-side); видалити власний акаунт не можна; якщо користувач є автором заявок/робіт/діагностик/коментарів — 400 «змініть роль» (`onDelete: Restrict` захищає історію аудиту) |

## Role-aware інтерфейс (нове, Lab 5)

- `src/lib/auth.ts` доповнено: `ROLE_RANK` + локаль `res.locals.can`:
  - `can.work` — майстер+ (статуси, роботи, запчастини, діагностика, коментарі, файли заявки);
  - `can.manage` — менеджер+ (заявки, клієнти, пристрої, оцінки, рахунки, оплати, гарантії, каталоги);
  - `can.admin` — адмін (користувачі).
- Шаблони (`requests/show.pug`, списки/картки клієнтів, пристроїв, каталогів)
  показують форми й кнопки **лише для ролей, яким дія доступна**; гість і
  відвідувач бачать суто read-only картки.
- Захист подвійний: UI хова дії, сервер (`requireRole`) відхиляє 403/302 —
  приховані кнопки не є механізмом безпеки.

## One-click launch (Windows)

Подвійний клік **`start.bat`** — перевіряє Docker, збирає образ, піднімає
PostgreSQL 18 + додаток, застосовує міграції, насичує демо-даними,
запускає сервер → **http://localhost:3000**.

Зупинити все — **`stop.bat`** (скинути дані: `docker compose down -v`).

## Тест-план (ручна/автоматична перевірка)

1. **Гість**: картка заявки `/requests/1` — без жодної форми/кнопки зміни;
   у шапці лише «Вхід».
2. **Відвідувач** (вхід `visitor@service.ua`): read-only; `/users` → редірект
   на `/login?next=%2Fusers`; `/clients/new` → 403.
3. **Майстер** (`tech1@service.ua`):
   - картка заявки: доступні форми діагностики, робіт, запчастин, коментарів,
     вкладень + кнопки статусу; оцінка/рахунок/оплати/гарантії — не видно;
   - `/users` → редірект на логін; `/clients/new` → 403;
   - списки клієнтів/пристроїв/каталогів — без кнопок «Новий…» і «Видалити».
4. **Менеджер** (`manager@service.ua`):
   - картка заявки: оцінка → «Оформити оцінку», «Видати рахунок», «Додати оплату», «Оформити гарантію»;
   - `/clients/new`, `/devices/new`, `/works/new`, `/parts/new` → 200, POST працює;
   - `/users` → редірект на логін (навіть авторизований).
5. **Адмін** (`admin@service.ua`):
   - в шапці посилання «Користувачі»;
   - `POST /users` (новий email/пароль) → у списку;
   - `POST /users/:id/edit` зміна ролі/ім'я → збережено;
   - видалення `visitor@service.ua` → 400 «прив'язаний до даних» (якщо є коментарі)
     або успішне видалення новозареєстрованого користувача;
   - видалення власного акаунта → 400.
6. `POST /register` (Lab 4) — новий акаунт `VISITOR`, автовхід.
7. Перевірка незмінності Lab 4: вхід/вихід, 401 за помилковий пароль, 403-сторінка.
